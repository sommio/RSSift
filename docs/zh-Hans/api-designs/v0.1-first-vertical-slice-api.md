# rss-start v0.1 内第一个垂直切片 API 设计

## 概览

这份设计文档把 `rss-start v0.1` 内第一个垂直切片的对外 API 合同固定为一个极简只读面：客户端只读取已经准备好的阅读条目，不控制 feed 拉取、刷新、摘要生成或失败恢复。

这里定义的是 v0.1 里面的第一个切片，不是整个 v0.1 的完整产品合同。这个切片的目标是先用最小可运行 API 把产品跑起来；更完整的 LLM 摘要生成能力会在后续切片中继续落地。

它承接 `docs/zh-Hans/plans/2026-04-09-002-feat-v0-1-first-vertical-slice-api-plan.md`，并把 plan 中已经达成的设计决策沉淀成 durable docs，供后续 `apps/api`、`apps/web` 和共享类型设计对齐。

## 设计目标

- 为桌面端双栏阅读器提供最小可用的读路径合同。
- 把外部合同压缩到“列表 + 详情”两个读取接口。
- 让客户端始终面向 prepared reading items，而不是后台工作流。
- 提前写清楚哪些内容不属于 v0.1 第一个切片，避免实现阶段范围膨胀。

## 非目标

- 这个第一切片不提供刷新、重试、摘要生成、feed 管理或状态查询接口。
- 不把内部抓取失败、正文缺失、摘要失败编码为对外字段。
- 不设计分页、筛选、排序参数、鉴权、多用户、已读或收藏。
- 不约束数据库 schema、任务队列、缓存或摘要算法实现细节。

## Contract Summary

| Method | Path | Consumer use | Returns |
|---|---|---|---|
| `GET` | `/articles` | 左栏扫读列表 | `ArticleListItem[]` |
| `GET` | `/articles/:id` | 右栏文章详情 | `ArticleDetail` |

## Resource Semantics

### `GET /articles`

这个接口服务于左栏：用户扫描标题、来源与发布时间，并且可以直接打开原文链接。

返回字段固定为：

- `id`
- `title`
- `sourceTitle`
- `publishedAt`
- `originalUrl`

设计约束：

- 不返回 `summary`。
- 不返回状态字段。
- 不返回控制动作。
- 返回值代表“已经准备好可以展示在列表中的文章”。

响应草图：

```json
[
  {
    "id": "article_001",
    "title": "Example article title",
    "sourceTitle": "Example Feed",
    "publishedAt": "2026-04-09T08:00:00Z",
    "originalUrl": "https://example.com/article-1"
  }
]
```

### `GET /articles/:id`

这个接口服务于右栏：用户查看单篇文章的最小判断材料，然后决定是否打开原文链接。

返回字段固定为：

- `title`
- `sourceTitle`
- `publishedAt`
- `summary`
- `originalUrl`

设计约束：

- `summary` 被视为服务端已准备好的字段，而不是需要客户端触发生成的资源。
- 不返回 `summaryStatus`、`contentAvailable`、`excerpt` 等扩张字段。
- 不暴露内部准备链路的阶段性信息。

响应草图：

```json
{
  "title": "Example article title",
  "sourceTitle": "Example Feed",
  "publishedAt": "2026-04-09T08:00:00Z",
  "summary": "This is a short deterministic summary prepared by the server.",
  "originalUrl": "https://example.com/article-1"
}
```

## Field Definitions

| Field | Meaning | Notes |
|---|---|---|
| `id` | 稳定文章标识 | 仅用于详情读取；最终编码形式延后到实现阶段决定 |
| `title` | 这个第一切片暴露的文章标题 | 当前切片先保持字段最小化；后续切片可以再与目标语言输出能力对齐 |
| `sourceTitle` | feed/source 的可显示名称 | 应适合列表与详情直接展示 |
| `publishedAt` | 文章发布时间 | 具体时间格式规则延后到实现阶段固定 |
| `summary` | 已准备好的简要摘要 | 这个第一切片允许由简单非 LLM 方案生成；后续切片可以升级到 LLM 生成 |
| `originalUrl` | 原文链接 | 列表和详情都必须返回 |

## Contract Invariants

- 对外只存在两条读路径：`GET /articles` 与 `GET /articles/:id`。
- 客户端永远只消费 prepared reading items。
- 这个切片先保持标题字段最小，不把后续 v0.1 切片锁死在同一标题生成策略上。
- 在这个第一切片里，摘要可以来自简单非 LLM 方案。
- 列表和详情都支持跳转原文。
- 内部失败与后台动作不进入外部合同。

## Explicitly Out of Contract

以下字段或动作即使未来内部存在，也不属于 v0.1 内第一个垂直切片的公共 API：

- `summaryStatus`
- `contentAvailable`
- `excerpt`
- `translation`
- `regenerateSummaryAction`
- `refreshFeedAction`
- 失败原因与重试建议
- `POST /articles/:id/summary/generate`
- `POST /feeds/:id/refresh`

## Deferred to Implementation

以下问题不影响当前 API 合同，但必须在进入代码实现时明确：

- `id` 的最终编码形式。
- `publishedAt` 的最终序列化格式。
- `summary` 在正文不足时的内部生成策略。
- 服务端如何从 `config.opml` 触发初次准备与后续刷新。

## Implementation Guidance

- `apps/api` 的实现应把这份文档视为外部合同锚点，而不是把实现结构反推成合同。
- `apps/web` 的数据获取层应直接围绕这里定义的字段集合建模，不应自行添加状态字段假设。
- 如果未来需要分页、刷新或更丰富的摘要状态，应通过新的 brainstorm/plan 扩展，而不是直接改写当前文档。

## Change Policy

只有在以下情况才应该修改这份文档：

- 产品语义真的发生变化；
- 这个位于 v0.1 内的第一个垂直切片 API surface 被明确扩张；
- 中英文文档需要同步修正以消除语义漂移。

如果变更属于从这个第一切片继续扩展到后续 v0.1 切片，应显式更新成对的中英文文档，而不是把这个第一切片的合同静默当成整个 v0.1 的最终合同。

如果变更只是实现细节，应更新 implementation plan 或代码注释，而不是污染当前合同文档。
