# 前端设计原则

这是一份面向设计师与 agent 的前端设计原则文档。

它服务整个 monorepo 的前端工作，但重点不是技术实现细节，也不是组件 API 清单，而是帮助人和 agent 在做页面时形成一致的设计判断、协作方式与验收口径。

这份文档是高层原则文档，不替代 `AGENTS.md`。`AGENTS.md` 负责仓库级执行纪律、skills 调用与工程约束；本文负责设计原则、设计判断与视觉验收标准。

未经用户明确许可，agent 不应主动修改本文。

## 设计优先级

默认按下面的顺序做取舍：

1. 用户任务与可用性
2. 产品感与审美质量
3. 组件系统与一致性

这三个维度都重要，但优先级必须清楚。组件、规范与复用存在的意义，是支撑页面体验，而不是反过来主导页面。

## 核心原则

### 从任务出发，不从组件出发

先回答用户来这个页面是为了完成什么，再决定页面该长什么样。不要因为某个组件顺手、某种布局熟悉，就倒推出页面结构。

### 一个页面只表达一个清晰意图

页面可以复杂，但意图不能混乱。用户一眼应该知道这里是读、选、填、比、管，还是看结果。不要把多个互相竞争的主叙事堆在同一个首屏里。

### 先让默认态成立

先把最常见、最核心的默认态做对，再补空态、错误态、加载态和边缘情况。默认态不成立，后续状态再完整也只是精致的噪音。

### 信息层级必须稳定

标题、摘要、元信息、正文、操作区要形成稳定层级。用户应当能快速扫读，也能自然进入细读。不要让每一块都在争夺注意力。

### 视觉应该有判断，但不要过度表演

界面可以有气质，但不应靠夸张的标题、过强的对比、刻意的装饰来证明自己“被设计过”。好的前端设计首先让使用顺手，其次才是让人觉得漂亮。

### 优先做减法

信息、操作、装饰、说明文案都应当克制。每多一块内容，都要说明它是否真的帮助用户完成当前任务。拿不出理由，就删。

### 局部成立，不代表整体成立

不要只盯着单个卡片、单个按钮或单个 section。前端设计的质量来自整体节奏、对齐、留白、密度和上下文一致性。局部精致但整体发散，仍然是低质量界面。

### 不覆盖用户的基本预期

尤其是阅读、输入、浏览这类高频任务，不要为了“新鲜感”破坏用户对布局、层级、滚动、点击位置和信息顺序的基本预期。

## 不同页面的轻量方法

本文不提供一套僵硬分类法，但不同页面的设计重点确实不同。

### 阅读 / 信息消费类

重点是阅读效率、节奏、层级、可持续停留。界面应当服务内容，而不是与内容竞争。

### 工具 / 表单类

重点是清晰、反馈、容错与完成路径。不要让用户猜下一步，也不要把表单做成展示页。

### 列表 / 管理类

重点是扫描效率、信息密度与操作可预期。不要把每个列表项都做成情绪化卡片。

### 展示 / 叙事类

重点是信息编排、视觉节奏与品牌表达。但即便是展示页，也仍然需要清晰的主线，而不是堆一页看起来“很满”的区块。

## 阅读器 / 信息消费类页面

阅读器不是 landing page，也不是杂志封面。它首先是一个让人稳定阅读的界面。

### 阅读效率高于装饰性

标题、摘要、元信息、正文和必要操作应当围绕阅读本身组织。所有额外表达都要服从这个目标。

### 版心、行长与留白服务阅读

正文区域要让人愿意停留，而不是只在截图里好看。大屏下应保持稳定、舒服的阅读列，不要无限铺满；同时也不要因为过度收窄而导致界面显得松散无力。

### 不重复呈现同一信息

同一组标题、摘要、元信息不要在多个区块重复出现，更不要用“总结一下”“一眼看懂”之类的伪增益模块挤压正文空间。

### 层级要克制而稳定

阅读器里的标题不应像营销页 hero；元信息不应抢正文；操作区不应比内容更显眼。重点是让用户自然进入正文，而不是被界面不断打断。

### 大屏下保持居中的阅读感

当视口放大时，阅读区应保持稳定中轴，并在合理范围内动态变宽。不要贴边，也不要让内容在巨大的空白里失去支撑感。

### 不替用户做多余决定

阅读器要尊重用户已有的阅读习惯。不要随意覆盖用户对字体、阅读方式或信息展开顺序的基本预期，除非产品目标明确要求这么做。

## 反模式

下面这些是需要主动警惕的低质量前端信号。

### AI slop

看起来完整，但没有明确意图；块很多，判断很少；像模板拼装，不像真的产品页面。

### 把所有页面都做成营销页

不是每个页面都需要大标题、大口号、大面积视觉宣言。工具页、阅读器、管理页首先要好用，而不是先“震撼”。

### 过度设计的标题层级

标题过大、过重、过密，会直接破坏信息层级，尤其在阅读器和工具页里最容易失控。

### 重复信息块

如果一个区块只是用另一种说法重复已经存在的信息，它通常不值得存在。重复不仅浪费空间，也会稀释主内容。

### 为了统一而牺牲体验

一致性很重要，但不能为了组件看起来统一，就让页面失去清晰的任务导向和上下文适配。

### 只看代码，不看截图

前端不是纯文本产物。只看 JSX、CSS 或 token 不能代表设计已经成立。没有截图验收的前端交付，不算完成。

## Agent 工作方式

### 先理解任务、页面类型与当前阶段

动手前先判断这是阅读、填写、管理还是展示页面；是 MVP、可用性修正，还是视觉打磨。不要在目标还没对齐时直接进入实现。

### 先给出一个清晰方向，再开始堆细节

避免同时尝试多种互相冲突的视觉方向。先让整体成立，再修节奏、密度、层级和局部组件。

### 前端改动后必须截图验收

只要改动影响页面结构、视觉层级、间距、响应式或交互感知，agent 就必须自己用 `agent-browser` 进行截图验收。

### 基于截图继续迭代

截图不是留档动作，而是设计反馈回路。agent 需要根据截图判断哪里仍然别扭、拥挤、松散、失衡或跑偏，并继续修改，直到达到可接受质量。

### 截图落盘位置

截图与相关浏览器验收产物统一放在 `.cache/agent-browser/`。

### 不要把原则文档当作可随手重写的执行细节

本文用于稳定设计判断。除非用户明确要求，否则 agent 不应为了某次具体实现方便而随意改写本文。

## 与 `AGENTS.md` 的关系

- `AGENTS.md` 负责执行纪律、技能调用顺序、架构与工程约束。
- `frontend-design.md` 负责设计原则、页面判断与视觉验收口径。
- 如果出现重叠，优先遵守 `AGENTS.md` 的执行约束，同时保持本文的设计意图不被稀释。

## 维护原则

### 保持短、小、可执行

如果一条内容必须依赖大量补充解释才能成立，它大概率不适合写进这里。

### 优先更新原则，不堆碎规则

这份文档应当帮助未来判断，而不是变成又长又僵硬的规则仓库。

### 中英双语保持同步

`docs/zh-Hans/frontend-design.md` 与 `docs/en/frontend-design.md` 必须保持语义同步；更新其中一份时，应同步更新另一份。
