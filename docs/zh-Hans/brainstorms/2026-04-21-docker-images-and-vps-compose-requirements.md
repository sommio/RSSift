# Docker 镜像与 VPS Compose 需求文档

## 问题背景

当前仓库已经有可部署的 `apps/web` 与 `apps/api`，但还没有容器资产，也没有单机部署路径。下一步需要为两个应用补齐面向生产的 Docker 镜像，并提供一套直接对应当前产品形态的 VPS 部署方式：单机、API 单进程假设、内置 PostgreSQL、反向代理统一入口。

这件事重要，因为项目需要一条可重复的自托管操作路径：从仓库 checkout 到完整服务启动，中间不必先引入镜像仓库、多节点编排或平台专属部署逻辑。

## 需求

**镜像打包**

- R1. 仓库必须为 `apps/web` 提供一个面向生产的 Docker 镜像。
- R2. 仓库必须为 `apps/api` 提供一个面向生产的 Docker 镜像。
- R3. 镜像方案必须保持 Turborepo monorepo 的结构边界，不能把 app 专属职责或共享 package 职责塌缩到仓库根目录。

**部署拓扑**

- R4. 仓库必须提供一条基于 Docker Compose 的单机部署路径，同时运行 `web`、`api`、`postgres` 和反向代理。
- R5. 默认 Compose 拓扑必须让 PostgreSQL 只在 Compose 内网中可达，默认不暴露宿主机端口。
- R5a. 默认 PostgreSQL service 不得定义面向宿主机的 `ports` 发布。如果后续为了本机调试临时增加宿主机可见映射，也只能绑定到 `127.0.0.1`，不能绑定到 `0.0.0.0`。
- R6. 默认 Compose 拓扑必须兼容当前 API 的运行时假设：唤醒触发的自动刷新仅支持单进程，不是多副本部署。
- R7. 外部流量必须先进入反向代理层，而不是把应用原始端口作为主要公网入口直接暴露。
- R8. 首次交付的反向代理必须选择 Caddy。

**运维流程**

- R9. VPS 运维者必须能够直接在服务器上基于仓库完成构建并启动整套服务，而不要求预先配置镜像仓库或 CI 镜像发布流程。
- R10. 部署流程必须兼容当前已定义的 app 运行时输入，尤其是 `apps/api/README.md` 中记录的配置，以及 `apps/web/package.json` 和 `apps/api/package.json` 中现有启动命令。
- R11. 交付的部署路径必须适合单机自托管场景，并清楚说明运维者如何提供环境变量、持久化数据以及 `apps/api` 拥有的订阅输入。
- R12. 部署路径必须把 `apps/api/feeds.opml` 视为运维者拥有的输入。API 容器必须通过运维者手动指定的宿主机路径 bind mount 来消费它，而不是把 feed 订阅烘焙进镜像、通过命名卷初始化，或作为仓库默认部署载荷的一部分交付。

## 成功标准

- 运维者可以在 VPS 上 clone 仓库，并通过有文档说明的 Compose 流程启动 `web`、`api`、PostgreSQL 与 Caddy 的完整栈。
- 默认部署不会把 PostgreSQL 发布到宿主机网络。
- 部署路径不假设 API 支持水平扩容。
- 首版部署路径不引入镜像仓库发布复杂度，而是聚焦在目标主机本地构建镜像。
- 运维者可以为 feed 订阅文件手动指定宿主机路径并挂载给 API 服务。

## 范围边界

- 本次不包含 GitHub Actions 或镜像仓库发布流程。
- 本次不包含 Kubernetes、ECS、Nomad 或多机编排。
- 本次不尝试让 API 支持多副本 ingestion 或分布式 wake-refresh 协调。
- 首次交付不要求同时支持多种反向代理。
- 默认不要求把 PostgreSQL 暴露给宿主机。
- 不要求支持把 PostgreSQL 公开绑定到 `0.0.0.0`。

## 关键决策

- 两个独立应用镜像 + 一个 Compose 栈：既保持 `apps/web` 与 `apps/api` 的部署所有权边界，又给运维者提供单机一条命令的启动方式。
- 由 Compose 管理 PostgreSQL：符合当前预期的首版自托管路径，也避免依赖宿主机上预先存在的数据库服务。
- PostgreSQL 仅内网开放：避免与宿主机数据库服务冲突，也降低误暴露风险。
- 如果未来确实需要为了调试临时开放 PostgreSQL 的宿主机访问，也只能作为 loopback 例外绑定到 `127.0.0.1`；公开绑定 `0.0.0.0` 不属于首版支持路径。
- 首个反向代理选 Caddy：在单机 VPS 场景下运维摩擦最小。
- 镜像仅在服务器本地构建：让首个里程碑先聚焦“能部署起来”，后续再补 registry 与 CI/CD 复杂度。

## 备选方案

- 先只做 `apps/api` 镜像：更简单，但不能给完整产品提供统一部署路径。
- 只交付镜像，不交付 Compose：能缩小眼前范围，但会把首次 VPS 部署的大量组装工作转嫁给运维者。
- 现在就接入 CI 发布镜像：后续有价值，但对首个自托管里程碑来说复杂度过高。
- 首个反向代理用 Nginx：可行，但对当前单机路径来说不如 Caddy 省心。

## 依赖 / 假设

- `apps/web` 继续作为独立可部署的 Next.js 应用存在。
- `apps/api` 继续作为独立可部署的、依赖 PostgreSQL 的 NestJS 应用存在。
- PostgreSQL 持久化、应用环境变量以及 feed 订阅输入都需要在规划阶段明确是由运维者通过挂载或卷来提供。
- feed 订阅文件是用户管理内容，不是镜像内静态部署资产。
- `apps/api/README.md` 中记录的 API 单进程行为约束，在这个里程碑里继续视为可接受部署前提。
