# rss-start v0.1 first vertical slice API design

## Overview

This design doc fixes the public API contract for the first vertical slice within `rss-start v0.1` as a minimal read-only surface: the client reads prepared reading items only and does not control feed fetching, refresh, summary generation, or failure recovery.

This is intentionally the first slice inside v0.1 rather than the full v0.1 product contract. The goal of this slice is to get the product running end-to-end with the smallest workable API surface first; richer LLM-driven summary generation can be added in a later slice.

It extends `docs/en/plans/2026-04-09-002-feat-v0-1-first-vertical-slice-api-plan.md` and turns the settled planning decisions into durable docs that later `apps/api`, `apps/web`, and shared-type work can align to.

## Design Goals

- Provide the minimum viable read contract for the desktop dual-pane reader.
- Compress the public surface to exactly two read endpoints: list and detail.
- Keep the client permanently pointed at prepared reading items rather than backend workflows.
- Record what is out of scope for the v0.1 first slice before implementation expands it accidentally.

## Non-Goals

- Do not provide refresh, retry, summary-generation, feed-management, or status-query endpoints in this first slice.
- Do not encode internal fetch failure, missing body content, or summary failure into public fields.
- Do not design pagination, filtering, sort parameters, auth, multi-user behavior, save/read state, or favorites.
- Do not constrain database schema, queues, caches, or summary algorithm implementation details.

## Contract Summary

| Method | Path | Consumer use | Returns |
|---|---|---|---|
| `GET` | `/articles` | Left-pane scannable list | `ArticleListItem[]` |
| `GET` | `/articles/:id` | Right-pane article detail | `ArticleDetail` |

## Resource Semantics

### `GET /articles`

This endpoint serves the left pane: the user scans title, source, and publication time, and may also open the source link directly.

The field set is fixed to:

- `id`
- `title`
- `sourceTitle`
- `publishedAt`
- `originalUrl`

Design constraints:

- It does not return `summary`.
- It does not return status fields.
- It does not return control actions.
- Every returned item already represents an article ready to appear in the list.

Response sketch:

```json
[
  {
    "id": "article_001",
    "title": "Example article title",
    "sourceTitle": "Example Feed",
    "publishedAt": "2026-04-09T08:00:00Z",
    "originalUrl": "https://example.com/article-1"
  }
]
```

### `GET /articles/:id`

This endpoint serves the right pane: the user inspects the minimum decision material for one article and then decides whether to open the source link.

The field set is fixed to:

- `title`
- `sourceTitle`
- `publishedAt`
- `summary`
- `originalUrl`

Design constraints:

- `summary` is treated as a server-prepared field rather than a resource the client triggers.
- It does not return expansion fields such as `summaryStatus`, `contentAvailable`, or `excerpt`.
- It does not expose stage-by-stage internal preparation state.

Response sketch:

```json
{
  "title": "Example article title",
  "sourceTitle": "Example Feed",
  "publishedAt": "2026-04-09T08:00:00Z",
  "summary": "This is a short deterministic summary prepared by the server.",
  "originalUrl": "https://example.com/article-1"
}
```

## Field Definitions

| Field | Meaning | Notes |
|---|---|---|
| `id` | Stable article identifier | Used only for detail lookup; final encoding is deferred to implementation |
| `title` | Article title exposed by this first slice | This slice keeps the field minimal first; later slices may align it with configured-language output |
| `sourceTitle` | Display name of the feed/source | Should be directly usable in list and detail views |
| `publishedAt` | Article publication time | Exact time-format rules are deferred to implementation |
| `summary` | Prepared short summary | This first slice may use a simple non-LLM strategy; later slices may upgrade this to LLM-generated output |
| `originalUrl` | Source article link | Must be returned by both list and detail |

## Contract Invariants

- The public surface contains only two read paths: `GET /articles` and `GET /articles/:id`.
- The client always consumes prepared reading items.
- This slice keeps the article title field minimal first and does not lock the later v0.1 slices to the same title-generation strategy.
- In this first slice, summaries may come from a simple non-LLM strategy.
- Both list and detail support opening the source article.
- Internal failures and backend actions do not enter the external contract.

## Explicitly Out of Contract

Even if these concepts exist internally later, they are not part of the public API of the first vertical slice within v0.1:

- `summaryStatus`
- `contentAvailable`
- `excerpt`
- `translation`
- `regenerateSummaryAction`
- `refreshFeedAction`
- failure reasons or retry suggestions
- `POST /articles/:id/summary/generate`
- `POST /feeds/:id/refresh`

## Deferred to Implementation

These questions do not change the current API contract, but they must be resolved before code implementation lands:

- the final encoding of `id`
- the final serialization format of `publishedAt`
- the internal fallback strategy for `summary` when article body content is weak
- how the server triggers first preparation and later refreshes from `config.opml`

## Implementation Guidance

- Treat this document as the external contract anchor for `apps/api`, not as a reverse projection of implementation structure.
- The data-fetching layer in `apps/web` should model exactly the field sets defined here and should not invent status-field assumptions.
- If future work needs pagination, refresh, or richer summary state, expand through a new brainstorm/plan rather than rewriting the current contract in place.

## Change Policy

This document should change only when:

- product semantics truly change;
- the API surface of this first vertical slice within v0.1 is explicitly expanded; or
- the Chinese and English versions need a synchronized correction to remove semantic drift.

If the change is the planned expansion from this first slice to later v0.1 slices, update the paired Chinese/English docs explicitly rather than silently treating the first-slice contract as the whole v0.1 contract.

If the change is purely implementation detail, update an implementation plan or code comments instead of polluting this contract doc.
